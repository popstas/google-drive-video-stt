# Spike: asking Meet what was recorded

Task 1 of `docs/plans/2026-09-18-meet-api-discovery.md`, run read-only against the
real domain. Every number below was measured, not read in a document; where a
document is the only source it says so.

## Verdict

**Go, as a discovery mode.** The API answers under domain-wide delegation, the
`start_time` filter works, and every recording it named carried the id of its file
in Drive.

**Not yet as the default.** One question is still open -- whether the list includes
conferences an employee attended but did not host (below). Until that is measured and
Task 7's `meet` against `walk` comparison comes out equal, the walk stays the default.

## What it took to get there

Two separate permissions, and they fail in different ways:

- The scope. `meetings.space.readonly` was authorized for the service account's
  client id; `meetings.space.created`, and every other scope tried as a control, was
  refused with `unauthorized_client` at token time. The grant is exactly as narrow as
  it should be.
- The API itself, enabled in the project the service account belongs to. Until it
  was, every call returned `403 PERMISSION_DENIED / SERVICE_DISABLED`. This is the
  error a new deployment meets first, and it says nothing about scopes -- worth
  translating on its own.

## Answers

**1. Does the list work under impersonation, and does the filter?** Yes to both.
Acting as an employee, `conferenceRecords.list` returned their conferences;
`start_time>="..."` narrowed them as documented, a window in the future returned an
empty list rather than an error, and an unsupported field returned
`400 INVALID_ARGUMENT / Invalid filter was provided`. Results come back newest
first; the documented page size is 25 by default and 100 at most, and a page size of
1 produced a `nextPageToken`, so paging is real.

**2. Does it include conferences the employee only attended?** **Not measured.** The
two accounts available for the spike have never been in the same call, so there was
nothing to compare. The documentation does not answer it either.

It decides real coverage, not a detail: a recording made by someone outside the
watched group reaches an employee's Meet folder only as a shortcut, and the walk
finds it there. If the API lists only hosted conferences, `meet` mode cannot see that
recording at all. Settle it by holding one call between two accounts of the domain
and asking both accounts for their conference list; an overlap answers yes.

**3. Does a recording carry its Drive file?** Yes -- every recording returned in the
window was in state `FILE_GENERATED` and carried `driveDestination.file`, and the
file opened as the employee. The documented states are `STARTED` (recording in
progress), `ENDED` (finished, file not generated yet) and `FILE_GENERATED`, and the
destination is only set in the last one. So "not ready yet" is a state to expect, and
a recording without a file id must be treated as waiting rather than absent.

**4. How long after a call does the file exist?** Between 5 and 8 minutes after the
conference ended, across every recording measured (the spread was about two and a
half minutes). The conference record itself exists as soon as the call ends, which is
the whole reason the mark may not advance past a conference whose file has not
appeared.

**5. Are transcripts listed the same way?** Yes. Each conference that had a recording
also had a transcript, in the same state, carrying the id of its Google Docs
document.

**6. What about an employee with nothing?** An empty list and no error. A call that
nobody recorded is returned as a conference with zero recordings -- the API reports
the call, not the artifact.

**7. What does it cost?** One list call per employee per window, then one recordings
call and one transcripts call per conference in it. Reading a month of one employee's
archive -- twelve conferences -- took 26 requests to Meet and 9 to Drive. In steady
state the window holds a handful of conferences, so a cycle is single digits per
employee and does not grow with the archive. Compare with the walk: 211 requests a
cycle today, growing with every meeting ever held.

## What this changes in the plan

- A conference that has not ended yet holds the mark. It has no recording because it
  is still happening, not because nobody recorded it.
- An employee whose query failed holds the mark where it is, so a fallback cannot
  quietly skip their conferences.
- The client asks for 100 per page and pages until the token runs out, and translates
  both failures: the missing scope and the disabled API.
