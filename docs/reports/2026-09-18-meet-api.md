# Spike: asking Meet what was recorded

Task 1 of `docs/plans/2026-09-18-meet-api-discovery.md`, run read-only against the
real domain. Every number below was measured, not read in a document; where a
document is the only source it says so.

## Verdict

**Go, as a discovery mode.** The API answers under domain-wide delegation, the
`start_time` filter works, and every recording it named carried the id of its file
in Drive.

Every question below is now answered by measurement, including the one that was open
when this report was first written. The `meet` against `walk` comparison came out
equal, on the same moment and by file id.

**Still not the default, and that is a deployment decision rather than a finding.**
The mode needs a scope an admin grants and an API enabled in a specific cloud project.
A deployment that has delegation but not those two would fail every cycle if this
became the default silently, so it is turned on by writing `run.discovery: meet`.

## What it took to get there

Two separate permissions, and they fail in different ways:

- The scope. `meetings.space.readonly` was authorized for the service account's
  client id; `meetings.space.created`, and every other scope tried as a control, was
  refused with `unauthorized_client` at token time. The grant is exactly as narrow as
  it should be.
- The API itself, enabled in the project the service account belongs to. Until it
  was, every call returned `403 PERMISSION_DENIED / SERVICE_DISABLED`. This is the
  error a new deployment meets first, and it says nothing about scopes -- worth
  translating on its own.

## Answers

**1. Does the list work under impersonation, and does the filter?** Yes to both.
Acting as an employee, `conferenceRecords.list` returned their conferences;
`start_time>="..."` narrowed them as documented, a window in the future returned an
empty list rather than an error, and an unsupported field returned
`400 INVALID_ARGUMENT / Invalid filter was provided`. Results come back newest
first; the documented page size is 25 by default and 100 at most, and a page size of
1 produced a `nextPageToken`, so paging is real.

**2. Does it include conferences the employee only attended? Yes -- and the attendee
cannot open the recording.** Measured by holding one call between two accounts of the
domain: the same conference id appeared in both accounts' lists, and the attendee's
list carried the recording with its Drive file id, in the same state as the
organiser's. Asking Drive for that file as the attendee returned **404**, while the
organiser -- who owns it -- read it normally.

So the API sees more than the walk, and Drive sees exactly as much. That is why
discovery leaves a recording owned by nobody configured alone: the file id it is
handed is not a file it can open, and a refusal treated as a failure would hold the
mark at that conference for ever, for work that is never going to be done here. A
call between two *configured* employees is a different case and the useful one: both
list it, one owns it, and it becomes a single piece of work attributed to the owner.

**3. Does a recording carry its Drive file?** Yes, once Meet has written it. Watched
live from the end of a call: the recording sat in state `ENDED` with no destination
for six minutes, then turned to `FILE_GENERATED` carrying `driveDestination.file`.
The documented states are `STARTED`, `ENDED` and `FILE_GENERATED`, and only the last
one carries a destination -- which the watch confirms rather than assumes. "Not ready
yet" is therefore a state to expect on any recent call, and a recording without a file
id must be treated as waiting rather than absent.

**4. How long after a call does the file exist?** Between 5 and 8 minutes after the
conference ended, across every recording measured (the spread was about two and a half
minutes); the call watched from its end took 383 seconds. The conference record itself
exists as soon as the call ends, which is the whole reason the mark may not advance
past a conference whose file has not appeared.

**5. Are transcripts listed the same way?** Yes. Each conference that had a recording
also had a transcript, in the same state, carrying the id of its Google Docs
document.

**6. What about an employee with nothing?** An empty list and no error. A call that
nobody recorded is returned as a conference with zero recordings -- the API reports
the call, not the artifact.

**7. What does it cost?** One list call per employee per window, then one recordings
call and one transcripts call per conference in it. Reading a month of one employee's
archive -- twelve conferences -- took 26 requests to Meet and 9 to Drive. In steady
state the window holds a handful of conferences, so a cycle is single digits per
employee and does not grow with the archive. Compare with the walk: 211 requests a
cycle today, growing with every meeting ever held.

## What this changes in the plan

- A conference that has not ended yet holds the mark. It has no recording because it
  is still happening, not because nobody recorded it.
- An employee whose query failed holds the mark where it is, so a fallback cannot
  quietly skip their conferences.
- The client asks for 100 per page and pages until the token runs out, and translates
  both failures: the missing scope and the disabled API.
- A recording the account cannot open is not a failure. Meet hands an attendee the
  file id of a recording they have no access to, and Drive answers 404. That is
  "somebody else's work", counted and skipped -- not an error, and not a reason to
  hold the mark.
- Placement runs inside the transient-retry wrapper, so it may not record a file as
  placed before the call as a whole has succeeded.
